# Incident — 2026-10-08: blind probing left the FM3 in its bootloader

**What happened.** While looking for a cab slot-DATA read, the agent probed `fn=0x7D`, `0x7E`, `0x7F` and
`0x79` as "read-shaped candidates" — they sit next to the cab IR upload trio (`0x7A`/`0x7B`/`0x7C`) — sending
each with a cab-shaped payload in both measured payload shapes. Hours later the unit was found showing

    Updating Firmware
    Transfer Error.
    Please reboot the device and try again.

and recovered only after a power cycle. The owner was not running an update and was not doing anything to the
unit: **this was caused by the agent's probing.**

**What is established, and what is not.**

- The unit **re-enumerated at 18:56:50** (its `/dev/ttyACM0` node was recreated), i.e. it rebooted into the
  update state.
- Those four function bytes ARE the **firmware-update family**: their refusals carry **image codes** —
  `0x11` *image size incorrect* and `0x14` *buffer overrun* — so the device was reading the probe frames as
  firmware-image traffic, not as queries.
- **The exact triggering frame is NOT established.** No frame tap had been enabled, so there is no record of
  what went out or in; `dmesg`/`journalctl` were unavailable and no USB-level capture was running. Every
  statement about the causal chain beyond the above would be invention.
- Ruled out with evidence: the verification gate (`verify-stack.sh`) contains **no device reference at all**,
  and nothing of the agent's was running when the screen appeared. No test opens the real port — the test
  files that mention `/dev/ttyACM0` use it as a MockTransport *label*.
- The unit was fully responsive between the probe and the incident (later probes, slot reads and writes all
  answered normally), so the effect was not immediate on the probe itself.

**Why it was avoidable, in the repo's own words.** This stack already carried the rule *"use prior captures as
fixtures rather than firing unprobed opcodes at a device holding a real IR library."* The probe violated it.
The aggravating factor is not the mistake but that the mistake was **unfalsifiable**: no tap, so the one thing
that would have named the frame did not exist.

**Recovery.** Power cycle. Fractal's documented recovery, if a reboot does not clear it: power on holding
**PAGE LEFT and PAGE RIGHT** until the **Emergency Utility** page appears. The FM3 has a built-in backup
firmware ROM, so a failed transfer is not a brick.

**Corrections this forces in the record.**

- The arm of the slot-data-read probe that used `0x7D/0x7E/0x7F/0x79` is **withdrawn as evidence about cabs**:
  those opcodes are firmware functions, so their behaviour says nothing about cab reads. The surviving
  evidence is the `fn=0x01` sub-action sweep (`0x4A`-`0x4E`, all implemented, none carrying a name or slot
  data), and even that leaves "no slot-data read exists" **probable** rather than measured.
- `fn=0x7D/0x7E/0x7F/0x79` must be labelled **firmware-update family** everywhere, not "refused/unknown".

**Guards now in force (shipped with this document).**

1. `FIRMWARE_FAMILY_FNS` + `isFirmwareFamilyFn` in `forgefx-midi/devices/gen3` — the family, named, with the
   evidence for why.
2. `guardFirmwareFamily()` wraps the transport in `openProbeSession()`, so it covers **every** probe script:
   a firmware-family frame throws before it is sent unless the run passes `--allow-firmware-family`. Pinned
   by a regression test that asserts the frame is never sent.
3. Every hardware probe now writes a **frame tap** by default (append-only, in/out, timestamped) — so the
   next incident is falsifiable instead of a story.
4. A rule in the skill: never send an unmeasured function byte to a unit holding a library; a sacrificial
   unit or a simulator only.
